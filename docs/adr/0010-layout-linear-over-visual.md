# 布局结构与线性交互流程优先于视觉风格

chameleon 历史不满的根因分析表明，真正的不满不是视觉风格（Fluent vs Apple vs Material），而是结构布局混乱（Quick Links 表单多字段挤一行、角色卡内多元素竞争焦点）与交互流非线性（多个操作平级呈现、流程分支不清晰、删除与主操作混在同一视觉层）。视觉风格只要一致即可——Naive UI 默认已满足。经过 grilling 决议：本产品的核心设计原则是「布局与线性交互优先于视觉风格」，所有设计决策以此为准。

**Considered Options**: 视觉风格优先（追求 Fluent 纯正度）——否决：历史证据表明视觉漂移是无底洞，每版改完都不满意；布局与交互优先——采纳：usability > aesthetics；一致的风格 + 清晰的布局 + 线性的流程 = 好用的工具。

**结构布局原则**：
1. 每个视图有且仅有一个主要焦点（primary focal point）
2. 相关元素分组，无关元素分离（Gestalt 接近性 / 相似性）
3. 垂直流优先（自上而下阅读顺序；水平排列仅用于并列、同质的选项）
4. 留白是结构的一部分，不是装饰
5. 卡片内部结构固定：**头部（标识 + 状态）→ 中部（内容）→ 底部（操作）**——所有卡片（角色卡 / 系统卡 / 沙箱卡）一致

**线性交互原则**：
1. 每个流程 = 一条直线：step 1 → step 2 → step 3，无分支
2. 每个视图只暴露一个主操作（primary action）；次要操作降权（位置靠右 / 视觉降权 / 放进 menu）
3. 表单字段垂直堆叠，从上到下填完即提交（提交按钮在最底部）
4. 删除 / 危险操作 = 独立的确认步骤（`n-popconfirm` 轻量确认 / `n-dialog` 重量确认），不混在主流程里
5. 不引入「模式」切换（modeless——避免改变 UI 含义的状态切换）

**Consequences**:
- Spec 与 tickets 必须按这两条原则审查——违反任一条的 PR 应被打回
- Naive UI 组件选择以「支持线性流程」为准：
  - `n-form` + `n-form-item` 默认垂直栈（满足原则 3）
  - `n-dialog` 用于模态确认（满足原则 4）
  - `n-popconfirm` 用于轻量二次确认（满足原则 4）
  - `n-card` 提供固定头 / 中 / 尾三段结构（满足布局原则 5）
  - 避免自创复杂交互（例如双面板联动、拖拽排序、mode switcher）
- 视觉决策降格为「跟随 Naive UI 默认 + Fluent token 覆盖」，不额外优化
- 未来的功能扩展必须先回答「这个新功能是哪个线性流程的一步」，否则不加入 UI
